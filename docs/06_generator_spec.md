# ТЗ на генератор данных NeoBank

## 1. Цель

Сгенерировать **реалистичные** данные за 12 месяцев (2024), которые **воспроизводят сюжет** из `docs/02_story.md`. Данные должны быть:

- **Связными** (клиенты → счета → карты → транзакции).
- **С грязью** (пропуски, дубликаты, TZ, опечатки).
- **С сюжетом** (метрики меняются по месяцам, A/B, fraud).
- **Воспроизводимыми** (seed).

## 2. Масштаб (параметры)

| Параметр         | Значение                | Обоснование                     |
| ---------------- | ----------------------- | ------------------------------- |
| Период           | 2024-01-01 — 2024-12-31 | 12 месяцев                      |
| Клиенты          | 500 000                 | Реалистично для необанка за год |
| Транзакции       | ~5 000 000              | ~10 на клиента                  |
| События          | ~25 000 000             | ~50 на клиента                  |
| A/B-эксперименты | 4                       | По сюжету                       |
| Seed             | 42                      | Воспроизводимость               |

**Почему 500 000 клиентов:** достаточно, чтобы работали статистические тесты (A/B, ML), но не настолько много, чтобы генерация заняла часы. Если компьютер слабый — можно уменьшить до 100 000 (параметр в конфиге).

## 5. Счета (`raw_accounts`)

**Логика:** каждый клиент получает **текущий счёт** при регистрации. Дополнительные счета (вклад, кредит) — при cross-sell.

| Поле           | Логика                                                                           |
| -------------- | -------------------------------------------------------------------------------- |
| `account_id`   | Auto-increment                                                                   |
| `client_id`    | FK                                                                               |
| `account_type` | `current` (все), `deposit` (с 7-го месяца, ~20%), `credit` (с 9-го месяца, ~15%) |
| `opened_at`    | Дата регистрации (для current) или дата cross-sell                               |
| `closed_at`    | NULL (90%) или дата ухода (10%)                                                  |
| `balance`      | Случайное: young 1 000–50 000, family 10 000–500 000, premium 100 000–5 000 000  |

## 6. Карты (`raw_cards`)

**Логика:** каждый клиент заказывает дебетовую карту при регистрации. Кредитную — при cross-sell (с 9-го месяца, ~15%).

| Поле           | Логика                                                 |
| -------------- | ------------------------------------------------------ |
| `card_id`      | Auto-increment                                         |
| `client_id`    | FK                                                     |
| `account_id`   | FK (текущий счёт для дебета, кредитный — для кредитки) |
| `card_type`    | `debit` (все), `credit` (15% с 9-го месяца)            |
| `issued_at`    | Дата заказа                                            |
| `activated_at` | Через 1–14 дней после выпуска (85% активируют)         |
| `status`       | `issued` → `active` → `blocked` (5%) / `closed` (5%)   |

## 7. Продукты клиента (`raw_products`)

**Логика:** каждый клиент имеет **счёт** и **дебетовую карту** с регистрации. Дополнительно:

- **Вклад** — с 7-го месяца (по сюжету cross-sell): 20% клиентов.
- **Кредитка** — с 9-го месяца: 15% клиентов.
- **Потребкредит** — с 9-го месяца: 5% клиентов.

## 8. Транзакции (`raw_transactions`)

### 8.1. Логика генерации

**Для каждого клиента:**

- Частота транзакций зависит от сегмента и месяца:
  - young: 15–25 в месяц.
  - family: 20–30 в месяц.
  - premium: 25–40 в месяц.
- **Сюжет:** частота растёт по месяцам (retention улучшается).

**Типы транзакций:**

- `purchase` (покупка) — 60%.
- `transfer` (перевод) — 20%.
- `payment` (оплата услуг) — 10%.
- `withdrawal` (снятие) — 5%.
- `top_up` (пополнение) — 5%.

**Суммы:**

- purchase: young 200–2000, family 500–5000, premium 1000–20000.
- transfer: 100–50000.
- withdrawal: 1000–50000.
- top_up: 500–100000.

**Категории (для purchase):**

- groceries (30%), transport (20%), entertainment (15%), utilities (15%), other (20%).

**Статусы:**

- completed (95%), declined (3%), reversed (2%).

**Fraud:**

- 0.5% транзакций — fraud (по сюжету: 0% в М1–5, 0.1% М6, 0.2% М7, 0.3% М8, 0.5% М9, 0.15% М10+ после внедрения ML).
- Fraud-паттерны: ночные транзакции, крупные суммы, новые устройства.

### 8.2. Поля транзакции

| Поле         | Логика                                                         |
| ------------ | -------------------------------------------------------------- |
| `tx_id`      | Auto-increment                                                 |
| `client_id`  | FK                                                             |
| `account_id` | FK                                                             |
| `card_id`    | FK (NULL для transfer)                                         |
| `date_id`    | Из `tx_at`                                                     |
| `tx_at`      | Timestamp (Moscow TZ для purchase, UTC для transfer — «грязь») |
| `amount`     | По типу и сегменту                                             |
| `tx_type`    | purchase/transfer/payment/withdrawal/top_up                    |
| `category`   | Для purchase; NULL для остальных                               |
| `status`     | completed/declined/reversed                                    |
| `is_fraud`   | TRUE/FALSE (по сюжету)                                         |

## 9. События (`raw_events`)

**Логика:** каждое действие клиента — событие.

| event_type   | Когда                            |
| ------------ | -------------------------------- |
| registration | При регистрации                  |
| verification | Через 1–3 дня (85%)              |
| login        | Каждый вход (2–10 в месяц)       |
| view_product | Просмотр продукта (5–20 в месяц) |
| open_product | Открытие продукта (cross-sell)   |
| transaction  | Каждая транзакция                |
| churn        | При уходе                        |

**Итого:** ~50 событий на клиента × 500 000 = 25 млн строк.

## 10. Fraud (`raw_fraud`)

**Логика:** для каждой fraud-транзакции — запись в `raw_fraud`.

| Поле          | Логика                                                               |
| ------------- | -------------------------------------------------------------------- |
| `fraud_id`    | Auto-increment                                                       |
| `tx_id`       | FK                                                                   |
| `client_id`   | FK                                                                   |
| `detected_at` | Через 1–7 дней после tx                                              |
| `fraud_type`  | card_not_present (60%), account_takeover (30%), friendly_fraud (10%) |
| `amount`      | Из tx                                                                |
| `confirmed`   | 80% TRUE, 20% FALSE                                                  |

## 12. «Грязь» (обязательно)

### 12.1. Пропуски

- `raw_clients.phone`: 15% NULL.
- `raw_clients.email`: 5% NULL.
- `raw_transactions.category`: 10% NULL.
- `raw_accounts.closed_at`: NULL для активных.

### 12.2. Дубликаты

- 0.1% дубликатов в `raw_events` (повторная запись).
- 0.05% в `raw_transactions`.

### 12.3. Часовые пояса

- `raw_events.event_at` — UTC.
- `raw_transactions.tx_at` — для purchase Moscow, для transfer UTC. **«Грязь».**

### 12.4. Опечатки в городах

- `Москва`, `москва`, `Moscow`, `Мск` — все в `raw_clients.city_name` (если денормализуем).
- **Но:** у нас `city_id` (FK) — опечаток нет. **Задача:** показать, что бывает. Добавим `raw_clients.city_name` (денормализация) с опечатками.

### 12.5. Строки вместо чисел

- `raw_transactions.amount` — 1% строк как `"1 500"` (с пробелом).

### 12.6. Неправильные типы

- `raw_clients.age` — 2% как `"25 лет"` (строка).

## 13. Формат вывода

**Куда:** Postgres, база `neobank`, схема `raw`, таблицы `raw_*`.

**Как:** pandas DataFrame → SQLAlchemy `to_sql()`.

**Батчами:** по 50 000 строк (чтобы не упасть по памяти).

## 14. Воспроизводимость

- **Seed:** 42 (фиксированный).
- **Все случайности** — через `np.random.default_rng(42)`.
- **Параметры** — в `data_generator/config.yaml`.
